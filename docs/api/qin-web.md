# QinWeb

QinWeb is Qin's lightweight HTTP and RPC layer.

The goal is a Qin-native fullstack API with a Hono-like developer experience and
a Native Image-friendly implementation. QinWeb should stay small: route handlers,
middleware composition, controller mounting, and RPC boundaries. Heavy runtime
reflection, classpath scanning, dynamic proxies, and servlet-container coupling
are not required for the core path.

## Package

```js
dependencies: {
    "com.qin:qin-runtime-core": "0.1.0",
    "com.qin:qin-web": "0.1.0"
}
```

Server Qin/TS code imports QinWeb through Java interop:

```ts
import { QinWeb } from "java:com.qin.web"
```

## Routes

```ts
import { QinWeb } from "java:com.qin.web"

export const app = QinWeb.create()
    .health()
    .get("/api/users", request => QinWeb.jsonRaw("{\"users\":[]}"))
    .post("/api/users", request => QinWeb.jsonRaw(201, request.bodyText()))
    .delete("/api/users/{id}", request => QinWeb.jsonRaw("{\"deleted\":\"" + request.param("id") + "\"}"))
    .toHttpApp()
```

`toHttpApp()` returns the lower-level `QinHttpApp` used by Qin's single-port
fullstack runtime.

## RPC

QinWeb supports named query and mutation handlers:

```ts
export const app = QinWeb.create()
    .query("UserController.getAll", request => QinWeb.jsonRaw("{\"users\":[]}"))
    .mutation("UserController.create", request => QinWeb.jsonRaw(201, request.bodyText()))
    .toHttpApp()
```

By default RPC is mounted at:

```text
POST /api/rpc/{method}
```

The path can be changed with `rpcPath("/rpc")`, which becomes `/rpc/{method}`.

## Controller Boundary

Qin fullstack can generate browser-compatible RPC clients from server-controller
imports. Application code can use the server controller like a normal object:

```js
import { UserController } from "../main/controllers/UserController.qin"

await UserController.getAll()
await UserController.create({ name })
await UserController.remove({ id })
```

The generated client is internal to Qin. User projects should not need checked-in
browser proxy files for QinWeb RPC.

## Native Image Constraints

QinWeb's long-term implementation should prefer:

- Static route tables generated by Qin compilation.
- Generated RPC clients and controller metadata.
- Explicit JSON helpers or generated codecs.
- No required runtime classpath scanning for core routing.
- No required dynamic proxies for controller dispatch.
- A small dependency surface suitable for GraalVM Native Image packaging.

This keeps the public API pleasant while keeping the runtime predictable enough
for `qin.exe` and native fullstack apps.
